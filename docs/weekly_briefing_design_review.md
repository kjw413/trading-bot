## 1. 한 문단 결론

**계산 코어는 그대로 쓸 수 있고, 껍데기는 요구사항과 맞지 않는다.** 이 저장소는
"자동매매 봇"(신호 → 주문 → 체결 → 상태)으로 설계돼 있는데, 다섯 요구사항은
"주간 모니터링·제안 서비스"(계좌 읽기 → 요약 → 전달)다. 다행히 팩터 계산·비중
산출·리밸런싱 계획은 이미 엔진과 브로커에서 분리돼 있어서
(`strategies/theme_multifactor.py:142` `generate_targets`,
`allocation/rebalance.py:30` `plan_rebalance`) 주문 코드를 한 줄도 만들지 않고
"제안"을 뽑을 수 있다. 반면 **계좌를 읽는 통로, 뉴스, 전달 수단, 실행 위치**는
네 가지 모두 지금 구조에 없거나 정반대로 잡혀 있다. 결론은 "구조를 갈아엎어라"가
아니라 **"코어는 유지하고 얇은 계층 3개를 옆에 새로 낸다"**이다.

한 가지 요구사항은 저장소의 사실과 정면으로 충돌한다 — 요구사항 4의 "**사전 검증된**
퀀트 알고리즘"인데, 이 저장소의 두 전략은 **둘 다 승격 판정에서 떨어졌다**(§4.4).
이건 기능이 덜 만들어진 게 아니라 전제가 아직 성립하지 않은 것이므로, 코드를
쓰기 전에 결정이 필요하다.

## 2. 요구사항 ↔ 현재 구조 대조표

| 요구 | 필요한 것 | 지금 있는 것 | 판정 |
|---|---|---|---|
| 1. 계좌 현황 read | 읽기 전용 계좌 조회 포트 | `Broker` ABC(주문·체결 11개 메서드), `KISBroker` 전부 미구현 | **포트 없음 — 신설** |
| 2. 뉴스·주가 동향 | 뉴스 수집·요약 | 없음 (grep 0건, M6~M19 계획에도 없음) | **전무 — 신설** |
| 3. 쉬운 워딩 | 용어를 한 곳에서 강제 | 부분적(`research evaluate` 결론문, `manual.html`) | **일관성 장치 없음** |
| 4. 매매 제안 | 검증된 알고리즘 + 제안 렌더링 | 계산 코어는 재사용 가능. **검증 통과 전략 0개** | **전제 미성립** |
| 5. 모바일 수신 | 클라우드 실행 + 푸시 | Windows PC + 작업 스케줄러 + Tkinter | **배포 모델 불일치** |

## 3. 지금 구조에서 그대로 쓸 수 있는 것 (재사용 자산)

낙관적으로 볼 근거가 실제로 있다. 다음은 손대지 않고 쓴다.

- **`generate_targets(dt, universe, data_store)`가 순수하다.**
  `strategies/theme_multifactor.py:142`는 `EngineContext`도, `Broker`도, 주문도
  참조하지 않는다. 날짜·유니버스·데이터저장소만 받아 목표 비중 dict를 낸다.
  요구사항 4의 "제안"은 이 함수 + `plan_rebalance` 두 개면 만들어진다.
  **체결 경로를 통과하지 않고 제안만 뽑는 것이 이미 구조적으로 가능하다** —
  이게 현재 설계의 가장 큰 자산이다.
- **`plan_rebalance`가 목표 비중을 매매 목록으로 바꾼다.**
  `allocation/rebalance.py:30`. `TradeIntent(symbol, side, qty, weight)`는
  그대로 "무엇을 얼마나" 제안 문장이 된다. `band=0.005` 무시 구간도 이미 있어서
  0.1%p 흔들림에 매주 매매를 제안하는 소음을 막아준다.
- **Point-in-Time 규율과 데이터 계층.** `data/panel.py`, `data/store.py`,
  `research/`는 요구사항이 바뀌어도 그대로 유효하다.
- **가격 staleness 가드.** `theme_multifactor`는 캐시가 `max_staleness_days`
  (기본 3거래일)보다 오래되면 리밸런싱을 건너뛴다. 제안 경로에도 **그대로 필요한**
  안전장치다 — 수집이 멈춘 줄 모르고 옛날 가격 기준 제안을 보내는 것이 최악이다.
- **`signal_id` 멱등성 원장**(`strategies/signals.py`). 스케줄러가 같은 주에 두 번
  돌아도 같은 제안을 두 번 알림하지 않게 하는 데 재사용된다.
- **1회 실행 + 파일 상태 설계.** `paper` 명령이 루프가 아니라 1회 실행을 권장
  형태로 잡은 것(README "작업 스케줄러가 5분마다 한 번씩")은 클라우드 cron에
  **오히려 잘 맞는다.** 배포 위치만 바꾸면 되고 실행 모델은 바꿀 게 없다.

## 4. 요구사항별 상세 진단

### 4.1 요구사항 1 — 계좌 현황 read

**문제: 읽기 전용 통로가 없다.** `broker/base.py`의 `Broker` ABC는 체결
시뮬레이터 인터페이스다 — `submit`, `cancel`, `open_orders`,
`on_session_open`, `on_intraday_bars`, `on_session_close`,
`expire_day_orders`, `mark_to_market`, `position`, `cash`, `equity`.
지금 구조에서 잔고를 읽으려면 이 11개를 전부 구현해야 한다
(`broker/kis.py`는 전부 `NotImplementedError`).

그런데 **다섯 요구사항 어디에도 주문 제출이 없다.** 요구사항 4는 "제안한다"이다.
즉 1단계에서 주문 코드를 만들지 않으면 **버그가 실제로 돈을 잃게 하는 경로 자체가
존재하지 않는다.** 이건 게으름이 아니라 1단계에서 얻을 수 있는 가장 큰 안전
마진이다.

**처방:** `Broker`와 별개로 읽기 전용 포트를 신설한다.

```
AccountReader (포트)
    snapshot() -> AccountSnapshot
AccountSnapshot
    as_of, positions[symbol, qty, avg_price, last_price, currency], cash_by_currency
```

메서드 하나면 요구사항 1이 끝난다. `broker/`는 1단계에서 손대지 않는다.
나중에 실전 주문이 필요해지면 그때 `Broker`를 추가로 구현하면 되고, 두 포트가
같은 클래스에 살든 아니든 그건 그때의 문제다.

**`Portfolio`를 재사용하지 말 것.** `portfolio.py:22`의 `apply_fill`은 체결을
쌓아 평단을 **스스로 만든다**. 실계좌는 반대다 — 증권사가 준 수량·평단이 진실이고,
이쪽이 계산하면 어긋난다(수수료 처리·분할·배당재투자·타 경로 매매). 수익률
**계산 함수만** 공유하고 값 객체는 분리한다.

**빠진 것 두 가지 — 둘 다 1단계 필수다.**

1. **수익률의 정의.** `report/metrics.py`는 백테스트 전제(입출금 없음)로
   `equity/initial_cash - 1`을 쓴다. 실계좌는 입금·출금이 있어서 이 식이 틀린다.
   최소한 입출금 조정, 제대로 하려면 시간가중수익률(TWR)이 필요하다. "이번 주에
   50만원 넣었는데 수익률이 올랐다고 나온다"는 요구사항 3(쉬운 워딩)의 신뢰를
   한 번에 깨뜨린다.
2. **다통화.** `architecture.md` §9가 "현재는 한 프로세스가 한 시장·한 통화를
   담당하며 환율 변환이 없다"고 명시한다. 그런데 요구사항은 SOXL·TECL(USD)과
   국내 종목을 **한 계좌에서 같이** 본다. 원화 기준 종목별 수익률에는 환손익이
   섞이므로, "주가는 올랐는데 원화 수익률은 마이너스"를 설명할 수 있어야 한다.
   `data/macro.py:32`에 `usdkrw` 시리즈가 이미 있다 — 환산 자체는 어렵지 않고,
   **어느 기준으로 보여줄지 정하는 것**이 설계 결정이다. 권고: 원화 기준을
   기본으로 하고 "주가 변동 / 환율 변동"을 분리해 두 줄로 보여준다.

### 4.2 요구사항 2 — 뉴스·주가 동향

**현재 전무하다.** 뉴스 관련 코드 0건, M6~M19 실행 계획에도 항목이 없다.

**중요한 함정 하나.** `docs/superpowers/specs/2026-08-12-event-alpha-design.md`는
"Narrative / News / Novelty — **불가**: 타임스탬프 있는 기사 아카이브 없음"으로
이미 판정을 내려놨다. 이 판정을 요구사항 2에 그대로 적용하면 안 된다 — 그 "불가"는
**백테스트용 Point-in-Time 뉴스 아카이브**에 대한 것이고, 요구사항 2는 백테스트가
아니라 **읽기용 주간 요약**이다. 과거 아카이브가 필요 없으므로 지금 당장 가능하다.
이 구분을 문서에 못 박아 두지 않으면 나중에 "뉴스는 불가로 결론났다"며 잘못
차단된다.

**처방:** `data/news.py`를 신설하되 **`data/panel.py`(PIT 패널)에 넣지 말 것.**
패널에 들어가는 순간 팩터 신호로 오해되어 백테스트에 샐 수 있다. `state/news/`로
격리한다. 소스는 국내 = 네이버 검색 API(무료) + DART 공시(`data/fundamentals.py`의
`DartClient`, `data/events.py` 이미 있음), 미국 = yfinance news 또는 Finnhub 무료
티어.

**레버리지·지수 ETF의 두 가지 함정** (참고사항 1이 SOXL·TECL을 명시했으므로 이건
부수적 문제가 아니다):

1. **SOXL·TECL에는 회사 뉴스가 없다.** 기초지수(SOX, NYSE Technology)와 주요 구성
   종목의 뉴스로 **매핑**해야 한다. 종목명으로 뉴스를 검색하는 단순 구현은 이
   종목들에 대해 빈 결과나 쓰레기를 낸다.
2. **주간 수익률이 기초지수의 3배가 아니다.** 레버리지 ETF는 일간 리셋이라
   변동성 감쇄가 있다. 요구사항 3(비전문가 워딩)과 정면으로 충돌하는 지점이다 —
   "3배 ETF인데 지수가 1% 올랐을 때 3%가 아니라 2.1% 올랐다"를 설명해야 한다.
   기능이 아니라 **워딩 설계의 핵심 과제**로 다뤄야 한다.

### 4.3 요구사항 3 — 쉬운 워딩

**부분적으로 있다.** `research evaluate` 리포트는 맨 위에 전문용어 없는 결론을
쓰고, `docs/manual.html`과 GUI는 초보자를 상정한다. 방향은 이미 맞다.

**문제는 일관성을 강제하는 장치가 없다는 것이다.** `report/report.py:57`은
"Equity Curve", "Drawdown", "DD %"를 그대로 쓰고, `report/metrics.py:22`의
`BacktestMetrics`는 `sharpe`, `profit_factor`, `exposure_pct`를 그대로 노출한다.
출력 경로가 하나 늘 때마다 각자 워딩을 새로 만들게 되어 있다.

요구사항 3은 "이 세션에서 개발 후 보고, 알림 등에서도 유효"라고 했다. 이 조건을
코드로 지키는 방법은 하나뿐이다 — **용어 사전을 한 곳에 두고 모든 출력이 그것을
거치게 한 뒤, 테스트로 강제한다.**

```
report/glossary.py:  지표키 -> (쉬운 이름, 한 줄 설명, 포맷)
테스트: 사용자에게 나가는 문자열에 금칙어(Sharpe, MDD, exposure, drawdown …)가
        가공 없이 나타나면 실패
```

이 테스트가 없으면 요구사항 3은 이번 한 번만 지켜지고 다음 기능에서 무너진다.

### 4.4 요구사항 4 — 사전 검증된 퀀트 알고리즘 기반 제안

**구조는 준비돼 있다** (§3). **전제가 성립하지 않는다.**

| 전략 | 판정 | 실측 |
|---|---|---|
| `theme_multifactor` (KR) | **승격 불가** | 벤치마크 대비 CAGR **−6.55%p**, MDD 33.04% (한도 25%), 비용 2배 검정 −3.52%p, walk-forward 승률 **측정 불가** |
| `us_asset_rotation` (US) | **승격 불가** | 두 벤치마크(SPY 매수보유 / 유니버스 동일비중) 모두 절대수익 미달 |

즉 요구사항 4를 지금 그대로 구현하면 **검증에서 떨어진 알고리즘의 매매 제안을
매주 받는 시스템**이 된다. 게다가 요구사항 3이 그 제안을 "쉬운 워딩"으로 감싸므로,
근거의 약함이 오히려 가려진다. 이건 이 검토에서 가장 큰 리스크다.

**추가 문제: 주간 리밸런싱 전제.** 요구사항 1이 "주단위 리밸런싱 가정"이라고 했다.

- `is_rebalance_date`는 `weekly`를 **지원한다**(`allocation/rebalance.py:72`).
  코드는 있다.
- 그러나 모든 설정 파일이 `rebalance = "monthly"`이고, **weekly로 승격 판정을 낸
  적이 한 번도 없다.** 위 두 판정 결과는 전부 월간 기준이다.
- 주간은 회전율을 크게 올린다. 승격 기준의 연 회전율 한도는 6.0(편도 600%)이고
  월간 실측이 3.42였다(`config/research.toml:52`). 주간으로 바꾸면 이 항목부터
  다시 재야 한다.

**즉 "주간 + 검증 통과"인 알고리즘은 현재 존재하지 않는다.** 세 가지 길이 있다.

| 선택지 | 내용 | 평가 |
|---|---|---|
| (a) 라벨 강제 | 제안에 승격 판정 상태를 **반드시** 표기 ("이 전략은 아직 검증을 통과하지 못했습니다 — 참고용") | 정직하지만, 매주 보다 보면 라벨은 읽히지 않게 된다 |
| (b) 4번을 뒤로 | 1단계는 현황+뉴스만, 제안은 검증 통과 후 | 가장 안전. 1단계 가치가 이미 충분(§6) |
| (c) 단순 규칙 먼저 승격 | 벤치마크를 넘는 단순 규칙 하나를 **weekly로** `research evaluate` 통과시키고 그것만 제안 | 근본 해결. 시간이 든다 |

**권고: (b)로 시작하고 (c)를 병행, 통과 전까지는 (a)로 표기.** 요구사항 4를
버리자는 게 아니라, 1·2·3·5가 알고리즘 없이도 즉시 가치를 내므로 4를 기다리게 할
이유가 없다는 뜻이다.

### 4.5 요구사항 5 — PC 없이 모바일 수신

**여기가 가장 크게 안 맞는다.** 현재 운영 모델 전체가 로컬 Windows PC 전제다.
README는 PowerShell `Register-ScheduledTask`, `.bat` 더블클릭, `E:\trading-bot`
경로로 쓰여 있고, 출력은 Tkinter GUI(`gui.py`, 820줄)와 로컬 HTML 리포트다.

**요구사항 5는 기능 추가가 아니라 배포 모델 변경이다.** 구체적 걸림돌 세 개:

1. **`pyproject.toml:39` — `[tool.uv] environments = ["sys_platform == 'win32'"]`.**
   락파일이 Windows 전용으로 풀려 있다. 리눅스 컨테이너에서 `uv sync`가 그대로
   되지 않는다. 이게 가장 구체적인 차단 지점이다.
2. **`truststore` 의존** (시스템 인증서 저장소) — 미국 데이터 수집 경로가 Windows
   인증서 저장소를 쓴다. 리눅스에서 동작 확인이 필요하다.
3. **`data/cache/`가 로컬 디스크 전제** — 클라우드 컨테이너는 휘발성이라 영속
   볼륨이나 오브젝트 스토리지가 필요하다. 주 1회 실행인데 매번 수 년치 일봉을
   다시 받는 건 낭비이자 실패 지점이다.

**좋은 소식:** 코드 자체는 옮기기 어렵지 않다. 순수 Python이고, 네트워크 의존
지점이 `data/sources.py`·`data/polling.py`로 분리돼 있고, 상태가 파일 기반이고,
CLI가 1회 실행 지향이다. **GUI에 묶인 로직이 없다** — `services.py`가 CLI와 GUI의
공통 진입점이라 서버에서는 CLI 경로만 쓰면 된다.

**처방:** 1단계는 GitHub Actions cron(무료, 이미 저장소가 GitHub에 있음) 또는 소형
VPS. 전달은 `notify/` 포트를 두고 구현 하나만 — **텔레그램 봇**을 권고한다(무료,
즉시 푸시, 이미지·문서 첨부 가능, 별도 앱 설치가 이미 돼 있을 가능성). 이메일은
백업.

**보안 주의:** 클라우드로 올리는 순간 **증권사 API 키가 내 PC 밖으로 나간다.**
읽기 전용 스코프로 발급할 수 있으면 반드시 그렇게 한다. 요구사항 1을 읽기 전용
포트로 짜야 하는 이유가 여기서 한 번 더 나온다 — 유출되더라도 주문이 안 되는
키라면 피해가 제한된다.

## 5. 참고사항 2에 대한 답 — 증권사 이동은 **불필요**하다

참고사항 2는 "토스증권 계좌현황 자동 READ 불가 시 다른 증권사 이동 추천"을
요청했다. **전제가 바뀌었다.**

- 토스증권이 2026년 5월 사전 신청을 받아 **2026년 8월 오픈API를 정식 출시**했다.
- 제공 범위: **국내·해외 통합 단일 API**, 계좌·보유주식 조회, 주문(일반·조건),
  실시간 시세, 종목 정보. OAuth 2.0이며 `client_id`/`client_secret`을 토스증권
  WTS의 설정 > Open API에서 **심사 대기 없이 직접 발급**한다.
- 즉 요구사항 1은 **증권사를 옮기지 않고** 충족 가능하다. 참고사항 1의 미국
  ETF(SOXL·TECL 등)도 같은 API로 조회된다.

**확인이 필요한 항목** (이 검토 환경에서 `developers.tossinvest.com` 접속이
프록시로 차단되어 공식 스펙을 직접 읽지 못했다 — 착수 전 반드시 확인할 것):

1. **읽기 전용 스코프**가 따로 있는가 — §4.5 보안 항목의 전제다.
2. 호출 제한(rate limit) — 주 1회 실행이라 여유롭겠지만 토큰 만료 주기는 확인.
3. **해외주식 잔고 응답에 원화 평가액·적용 환율이 포함되는가** — 오면 §4.1의
   다통화 작업이 크게 줄고, 안 오면 `usdkrw`로 직접 환산해야 한다.
4. 조건주문 API의 존재 — 지금은 안 쓰지만, 요구사항 4가 나중에 "제안"에서
   "집행"으로 갈 때의 선택지가 된다.

**그래도 포트는 만든다.** `AccountReader` 포트를 먼저 정의하고 토스 구현을 붙이면,
증권사 교체가 구현체 하나 갈아끼우는 일이 된다. KIS는 이미 스켈레톤과 모의투자
환경이 있으므로 백업으로 남는다. 참고사항 2의 리스크를 **구조로 흡수하는** 방법이다.

## 6. 종합 판정과 단계 제안

### 판정

**타당성: 코어는 타당, 껍데기는 부적합.** 갈아엎을 필요는 없다.

| 구분 | 대상 |
|---|---|
| **그대로 사용** | `factors/`, `allocation/`, `research/`, `data/store.py`, `data/panel.py`, `engine/calendar.py`, `theme_multifactor.generate_targets`, `strategies/signals.py` |
| **얇게 신설** | `account/`(읽기 전용 포트 + 토스 구현), `data/news.py`, `report/glossary.py` + 주간 브리핑 렌더러, `notify/`(텔레그램) |
| **1단계에서 손대지 않음** | `broker/`(주문 경로 전체), `engine/`(백테스트·모의투자), `gui.py` |
| **반드시 바꿔야 함** | 다통화 원화 환산, 입출금 반영 수익률(TWR), weekly 리밸런싱 재검증, 실행 위치(로컬 PC → 클라우드) |

### 단계

**0단계 (선행, 코드 아님).** 토스 오픈API 스펙 확인 — §5의 네 항목. 읽기 전용
스코프 유무가 이후 설계를 가른다.

**1단계 — 요구사항 1·3·5.** `AccountReader` + 주간 현황 브리핑 + 텔레그램 전달.
알고리즘 없이도 즉시 가치가 나오고, 주문 코드가 없으므로 **실패해도 돈을 잃지
않는다.** 여기서 워딩 사전과 테스트를 함께 만들어 요구사항 3을 구조로 고정한다.
클라우드 이전(리눅스 락파일, 캐시 영속화)도 이 단계에서 끝낸다.

**2단계 — 요구사항 2.** 뉴스 수집·요약. 레버리지 ETF의 기초지수 매핑을 처음부터
포함한다.

**3단계 — 요구사항 4.** 매매 제안. 단, weekly 기준 `research evaluate` 통과가
선행 조건이고, 통과 전에는 "검증 미통과" 표기를 강제한다.

### 이 순서를 권하는 이유

요구사항 4가 나머지 넷의 발목을 잡을 이유가 없다. 1·2·3·5는 알고리즘의 품질과
무관하게 성립하고, 4는 **저장소 바깥의 사실**(어떤 전략이 벤치마크를 이기는가)에
달려 있어 일정으로 밀어붙일 수 없다. 1단계를 먼저 돌리면 실계좌 데이터가 쌓이고,
그게 3단계에서 제안을 검증할 재료가 된다.

## 7. 착수 전 결정이 필요한 것

1. **요구사항 4를 1단계에 넣을 것인가**(§4.4의 a/b/c). 이 검토의 권고는 (b)+(c),
   과도기에는 (a).
2. **주간 리밸런싱을 유지할 것인가.** 유지한다면 weekly로 승격 판정을 다시 내야
   하고, 그때까지 월간 판정 결과는 근거로 쓸 수 없다.
3. **수익률 기준.** 원화 단일 기준 / 통화별 분리 / 주가·환율 분해 중 무엇을
   기본 화면으로 할 것인가.
4. **클라우드 실행 위치.** GitHub Actions(무료·간단, API 키를 GitHub Secrets에
   보관) vs 소형 VPS(캐시 영속화가 쉬움). 주 1회라면 Actions로 충분하다.
