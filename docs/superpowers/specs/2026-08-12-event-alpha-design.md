## 1. 한 문단 요약

기존 두 전략은 "좋은 팩터 값 → 상승"이라는 선형 가정 위에 있고, 둘 다 승격 기준에
미달했다. 다음 방향은 **같은 이벤트라도 그 직전 상태에 따라 결과가 다르다**는
가설을 검증하는 것이다. 다만 이 저장소에는 컨센서스 데이터가 없고 이벤트 표본이
70건뿐이라, 제안된 ML 파이프라인을 지금 만들 수 없다. 이 문서는 프로그램 전체를
**단계별 게이트**로 정의하고, 지금 실제로 착수 가능한 첫 단계(M1)만 상세 설계한다.

## 2. 문제

두 개의 검토 문서가 `State → Event → Reaction → Alpha` 구조와 LightGBM 기반
Event Alpha 모델을 제안했다. 저장소 실측 기준으로 그중 실행 가능한 것과 아닌 것이
갈린다.

| 제안 요소 | 이 저장소에서의 상태 |
|---|---|
| Point-in-Time / walk-forward / 승격 게이트 | **이미 있다** — `data/panel.py`, `research/` |
| 가격 기반 state 피처 | **가능** — 신규 데이터 0, 기존 `Factor` 하네스에 붙는다 |
| 공매도 포지셔닝 (KR) | **가능** — `pykrx`가 이미 의존성 |
| Expectation Engine (컨센서스·추정치 변화·분산) | **불가** — DART는 실제치만. 미국도 무료 PIT 컨센서스 없음 |
| Surprise Engine | **부분 가능** — 컨센서스 대신 시계열 SUE |
| Narrative / News / Novelty | **불가** — 타임스탬프 있는 기사 아카이브 없음 |
| LightGBM Event Alpha | **표본 부족** — 이벤트 ≈ 70건에 피처 40개 |

그리고 두 문서와 1차 검토가 함께 놓친 것이 하나 있는데, 이것이 나머지 전부의
전제다.

## 3. 전제 결함: 이벤트 날짜가 틀렸다

`data/fundamentals_panel.py`는 DART 정기보고서의 접수일(`rcept_dt`)을
`announcement_date`로 저장한다. **그 날은 시장이 실적을 알게 된 날이 아니다.**

한국 상장사는 정기보고서보다 앞서 **잠정실적을 공정공시로** 낸다. 4분기 잠정실적은
1월 초에 나오고 같은 숫자를 담은 사업보고서는 3월에 접수된다. 주가가 반응하는 것은
1월이다. (미국도 같다 — 8-K Item 2.02가 10-Q보다 앞선다.)

정기보고서 접수일을 이벤트일로 쓰면:

- pre-event state가 **이미 반응이 끝난 뒤의 상태**를 잰다
- immediate reaction이 **아무 일도 없었던 날**을 잰다
- 코드는 정상 동작하고 숫자도 나온다 — **그래서 위험하다**

`DartClient.disclosure_list`는 이미 `report_name`을 반환하므로, 어느 공시가
이벤트인지 판정하는 분류기만 추가하면 된다. 이것이 M1의 첫 번째 산출물이다.

## 4. 프로그램 구조와 단계 게이트

각 단계는 **다음으로 넘어갈 조건**을 갖는다. 조건을 못 채우면 다음 단계로 가지
않는다.

| M | 내용 | 넘어갈 조건 |
|---|---|---|
| **M1** | **이벤트 캘린더 + 이벤트 리스크 오버레이** (본 문서 §6) | 배관이 끝에서 끝까지 붙고 `research evaluate`가 오버레이 유무 차이를 낸다 |
| M2 | 유니버스 확장 — 미국 유동성 상위 300~500, 2010~, PIT 재구성 | 이벤트 후보 ≥ 3,000건, 생존자 편향 크기를 측정해 기록 |
| M3 | EDGAR `companyfacts` 수집 + 시계열 SUE | 이벤트당 pre-event state와 post-event 수익률이 모두 채워진 행 ≥ 3,000 |
| M4 | 최소 state 피처를 `Factor`로 | `research report`로 IC 측정이 실행된다 |
| M5 | **이벤트 스터디 / 가설 검정** ← go/no-go | SUE 5분위 × pre-runup 5분위 표에서 효과가 보인다 |
| M6 | 선형 baseline + interaction (null model) | OOS에서 효과 방향이 유지된다 |
| M7 | ML — baseline을 OOS에서 이길 때만. 승격 하네스 개조 동반 | OOS에서 baseline 초과 |
| M8 | 오버레이 배치 | 승격 기준 6개 통과 |

**M5가 이 프로그램의 판정 지점이다.** 3,000~5,000건 표본의 2차원 분위 표에서 효과가
보이지 않으면 LightGBM은 잡음을 찾을 뿐이므로, M6 이후는 실행하지 않는다.

### 4.1 왜 M1의 계획만 쓰는가

M2 이후의 설계는 앞 단계의 **측정 결과에 따라 달라진다.** M5의 분위 표를 보기 전에
M6·M7의 피처 목록과 모델 구조를 확정하는 것은, 이 저장소가 이미 비싸게 배운
"in-sample 스윕 승자를 그대로 채택하는" 실수와 같은 종류다. 계획은 게이트를 통과할
때마다 하나씩 쓴다.

## 5. 컨센서스 없이 서프라이즈를 정의하는 방법 (M3 선행 결정)

M3에서 쓸 정의를 미리 못박아 둔다. 컨센서스를 못 구하므로 PEAD 문헌의 원조 정의인
**계절 랜덤워크 기준 시계열 SUE**를 쓴다.

```text
ΔX_q = X_q − X_{q−4}                    # 전년 동기 대비 변화
δ    = 최근 8분기 ΔX 평균                 # drift
SUE  = (ΔX_q − δ) / σ(ΔX, 최근 8분기)
```

"시장의 기대"가 아니라 "단순 외삽 대비 서프라이즈"다. 이 차이를 리포트에 명시한다.

**선결 확인:** DART `fnlttSinglAcntAll`의 손익계산서는 보고서 종류에 따라
`thstrm_amount`가 3개월치일 수도 누적일 수도 있다. 현재 코드는 이 구분을 하지
않는다. 분기 차분 SUE를 만들기 전에 반드시 검증해야 한다 — 분기와 누적이 섞이면
값은 나오고 전부 틀린다.

## 6. M1 설계: 이벤트 캘린더 + 이벤트 리스크 오버레이

### 6.1 왜 이것이 첫 단계인가

**이벤트 리스크 오버레이는 컨센서스도 서프라이즈도 모델도 필요 없다. 실적 발표
"날짜"만 있으면 된다.**

가설: *실적 발표를 앞둔 종목의 비중을 발표 전 N일 동안 줄이면 위험조정 성과가
개선되는가?*

표본이 5종목뿐이라 성과 결론은 약하다. **이 단계가 확인하는 것은 성과가 아니라
배관이다** — 이벤트 날짜 수집 → PIT 저장 → 전략 반영 → 승격 하네스 판정까지 끝에서
끝까지 붙는가. 여기서 안 붙으면 미국 500종목을 수집해도 안 붙는다.

### 6.2 무엇을 이벤트로 볼 것인가

`DartClient.disclosure_list`가 주는 `report_name`으로 분류한다.

| 분류 | 판정 근거 (보고서명 부분일치) | 용도 |
|---|---|---|
| `provisional` | `영업(잠정)실적`, `매출액또는손익구조` | **이벤트일** |
| `periodic` | `분기보고서`, `반기보고서`, `사업보고서` | 잠정실적이 없는 기업의 대체 이벤트일 |
| (제외) | 그 외 전부 | 실적 이벤트가 아니다 |

`provisional`이 있으면 그것이 이벤트다. 없는 기업(중소형주에 흔하다)은 `periodic`을
쓰되, 패널에 `event_kind`를 남겨 어느 쪽인지 항상 구분 가능하게 한다. **두 종류를
한 컬럼에 섞어 놓고 구분을 못 하게 만드는 것이 §3에서 지적한 결함의 재발이다.**

### 6.3 다음 이벤트일을 PIT로 추정하는 방법

오버레이는 "발표 전"에 작동해야 하므로 미래 발표일이 필요하다. 그런데 미래 발표일을
지금 지식으로 채우면 그것이 look-ahead다. 따라서 **과거 이벤트 간격만으로 추정한다.**

```text
past      = available_at <= dt 인 이벤트들의 date, 오름차순
gaps      = 연속 이벤트 간 일수
estimate  = past[-1] + median(gaps)
```

규칙:

- 과거 이벤트가 4건 미만이면 간격의 중앙값을 믿을 수 없다 → **추정 불가(None)**
- 추정일이 이미 지났으면 "발표 임박"으로 보고 `days_to_event = 0`
- 다만 추정일이 **중앙값 간격 이상 지났으면** 발표 임박이 아니라 **데이터 수집이
  멈춘 것**이다 → 추정 불가(None). 이 가드가 없으면 파이프라인이 죽었을 때 전 종목이
  영구히 축소된 채로 남는다 (`_is_price_data_stale`와 같은 종류의 방어다)
- 추정 불가는 **오버레이 미적용**이다. 모르는 것을 근거로 포지션을 건드리지 않는다

### 6.4 오버레이 규칙

- 발동 조건: `0 <= days_to_event <= window_days`
- 동작: 해당 종목 보유 수량을 `scale`배로 **축소한다**
- 줄어든 비중은 **현금으로 간다.** 다른 종목에 재분배하지 않는다 —
  `apply_constraints`가 집중도 초과분을 현금으로 보내는 것과 같은 원칙이다
- **축소만 한다.** 발표 후 복원은 다음 정기 리밸런싱에 맡긴다

축소 전용으로 제한하는 이유: 리밸런싱 밖에서 매수 경로를 새로 만들지 않기 위해서다.
가설이 "발표 전 노출 축소가 도움이 되는가"이므로 축소만으로 검정이 성립하고,
방향도 보수적이다. 한계로 문서화한다(§11).

### 6.5 리밸런싱 주기와의 충돌

현재 `on_bar`는 `is_rebalance_date`(월말)가 아니면 즉시 반환한다. **월 초 이벤트를
월말에 반영하면 의미가 없다.** 따라서 오버레이는 리밸런싱 게이트 **앞**에서 매일
평가한다.

```text
on_bar(dt):
    날짜 중복 방지
    → 이벤트 축소 평가 (매일)          ← 신설
    → is_rebalance_date 아니면 반환
    → 기존 리밸런싱
```

같은 이벤트에 대해 반복 축소하지 않도록, 종목별로 "어느 추정 이벤트일 때문에
축소했는지"를 전략 상태에 남긴다. 추정 이벤트일은 새 이벤트가 관측되기 전까지
안정적이므로 이벤트당 정확히 한 번 축소된다.

### 6.6 측정 방법

**신규 측정 코드가 없다.** `research evaluate`는 같은 전략을 두 설정으로 돌려
차이를 낸다(`cli.py:436`, `evaluation.py:360`).

```text
--config           config/kr_theme_event_overlay.toml   (오버레이 켬)
--benchmark-config config/default.toml                  (오버레이 끔)
```

두 파일은 오버레이 두 줄을 빼면 동일해야 한다. 그러면 초과수익·Sharpe·MDD·회전율의
차이가 **오버레이 효과 그 자체**다.

## 7. 구조

패널과 같은 메타데이터 규약(`source`, `available_at`, `data_version`)을 따른다.

## 8. 오류 처리

- 한 종목의 공시 조회가 실패해도 배치는 계속한다 (`update_flows`와 동일)
- DART API 키가 없으면 `MissingApiKeyError`로 파이프라인이 **실패가 아니라 생략**으로
  기록한다 (`fundamentals`와 동일)
- 이벤트 패널이 아예 없으면 `days_to_event`는 전부 None이고 오버레이는 **아무것도
  하지 않는다.** 데이터 없음이 조용히 "이벤트 없음"으로 둔갑해 포지션을 건드리면 안 된다
- 축소 주문 제출이 실패해도 나머지 종목은 계속 처리한다 (기존 리밸런싱 루프와 동일)

## 9. 테스트

전부 네트워크 없이 수행한다. DART 응답은 canned dict, 가격은 합성 fixture.

| 대상 | 검증 |
|---|---|
| 공시 분류 | 잠정실적/정기보고서/무관 3분류; 실제 DART 보고서명 문자열 |
| 이벤트 패널 | `available_at`이 접수일의 다음 거래일; 재수집 시 0행 |
| 다음 이벤트 추정 | 정상 간격; 이벤트 부족 시 None; 지난 추정일은 0; **오래 지난 추정일은 None** |
| 오버레이 | 창 안 축소; 창 밖 불변; None 불변; 축소분이 재분배되지 않음 |
| 전략 통합 | 리밸런싱 아닌 날에도 축소가 발생; 같은 이벤트에 두 번 축소하지 않음; 상태 복원 |
| 회귀 | 오버레이 비활성 시 기존 백테스트 결과가 **한 자릿수까지 동일** |

마지막 항목이 핵심이다. 오버레이가 꺼져 있을 때 기존 결과가 바뀌면, 그 뒤의 모든
비교가 오염된다.

## 10. 범위 제외

- **서프라이즈·컨센서스·뉴스·ML은 이번 범위가 아니다.** M1은 날짜만 쓴다
- 미국 시장은 이번 범위가 아니다. EDGAR 수집은 M3다
- 발표 후 복원 매수 경로는 만들지 않는다 (§6.4)
- 파라미터 탐색 금지. `window_days`와 `scale`은 처음 정한 값을 그대로 쓰고,
  in-sample에서 스윕해 고르지 않는다. 이 저장소는 그 실수의 실물 사례를 이미 갖고 있다
  (`us_etf_rotation_review.md`)

## 11. 알려진 한계

- **표본이 5종목이다.** M1의 성과 수치는 근거가 되지 못한다. 이 단계의 산출물은
  판정이 아니라 **작동하는 배관**이다
- 오버레이는 축소만 하고 복원은 다음 리밸런싱에 맡긴다 — 발표 직후 반등을 놓칠 수 있다
- 다음 이벤트일은 과거 간격의 중앙값 추정이다. 실제 발표일 공시(`실적발표(예정)일`)를
  쓰면 정확해지지만, 그 공시의 PIT 수집은 별도 과제다
- `PanelStore`의 키는 (date, symbol)이므로 **같은 날 같은 종목의 이벤트는 하나로
  합쳐진다.** 잠정실적과 정기보고서가 같은 날 접수되는 경우가 이에 해당하며,
  `event_kind` 우선순위로 `provisional`을 남긴다
- 선결 과제(범위 밖): 주문 사이징이 `min_cash_weight`를 미리 떼지 않아 주문의
  17~19%가 거부된다(`us_etf_rotation_review.md`). 이 결함은 오버레이 효과 측정도
  오염시킨다. M1 결과를 읽을 때 감안해야 하고, M2 전에 고치는 것이 바람직하다
