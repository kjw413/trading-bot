# Event Alpha 설계안 적용 검토 (2026-08-12)

대상: `trading_bot_event_alpha_context.md`가 제안한 **State-dependent Event Alpha**
구조를 이 저장소에 적용할 수 있는지에 대한 검토.

§1~§7은 1차 제안에 대한 검토다. 같은 날 도착한 재검토 문서
(`trading_bot_event_alpha_superpowers_review.md`)에 대한 2차 검토는 §8에 있다.
**§8.3은 §1의 판단 하나를 정정한다** — 1차 검토가 "이벤트 데이터셋 뼈대가 이미
있다"고 본 부분에 이벤트 날짜가 틀렸다는 문제가 있다.

## 결론

**설계 철학은 채택할 만하고 기존 규율과 충돌하지 않는다. 그러나 제안된 순서
그대로는 실행할 수 없다.** 막는 것은 코드가 아니라 데이터다.

1. **컨센서스 데이터가 없고, 무료로 구할 수 없다.** 설계안 §7 Expectation
   Engine 전체와 §8의 대부분이 컨센서스에 의존하는데, 이 저장소의 유일한
   재무 소스인 DART는 실제치만 제공한다.
2. **이벤트 표본이 약 70건이다.** 현재 유니버스는 KR 5종목(2023~)과 미국 ETF
   11종이다. ETF는 실적발표가 없으므로 이벤트 알파의 대상이 아니고, KR 5종목 ×
   4분기 × 3.5년 ≈ 70건이 전부다. 설계안 §18은 피처를 40개 이상 나열한다.
   표본 70에 피처 40으로 LightGBM을 돌리면 얻는 것은 과적합뿐이다.

이 두 번째 문제는 저장소가 **이미 스스로 진단한 것**이다.
`docs/us_etf_rotation_review.md`는 "11종을 5분위로 나누면 분위당 2.2종목이라
IC IR과 단조성이 통계적으로 불안정하다. 신호가 없어서가 아니라 유니버스가
작아서다"라고 적고 있다. 설계안은 이 사실을 모른 채 쓰였다.

따라서 **순서를 데이터 가용성 기준으로 뒤집으면 설계안을 거의 그대로 쓸 수
있다.** 수정 순서는 §4에 있다. 요지는 비용 0인 것부터 하고, 뉴스/LLM은 맨
마지막에 둔다는 것이다 — 설계안 자신의 "Price > Narrative" 원칙이 그 순서를
지지한다.

## 1. 이미 갖춰져 있어 새로 만들 필요가 없는 것

설계안이 요구하는 검증 규율은 대부분 이 저장소에 이미 구현돼 있다. 이것이
"이식이 가능하다"고 판단하는 근거다.

| 설계안 요구 | 기존 구현 | 상태 |
|---|---|---|
| §24.1 Point-in-Time | `data/panel.py` — `PanelStore.read(as_of=)`, `attach_metadata(available_at=...)` | 그대로 사용 |
| §24.2 Look-ahead 방지 | 종가 신호 → 다음 시가 체결 (`docs/architecture.md` §3) | 그대로 사용 |
| §24.3 Walk-forward | `research/walk_forward.py`, `research/evaluation.py` | 수정 필요 (§3.6) |
| §24.5 비용 포함 | `broker/fees.py`, `evaluation.scale_costs` (2배 검정) | 그대로 사용 |
| §25 평가 지표 | `research/ic.py`, `research/quantiles.py`, `report/metrics.py` | 그대로 사용 |
| §26 팩터 채택 판정 | `research/gate.py` + `[factor_gate]` | 그대로 사용 |
| §21 Structural + Event 결합 | `factors/transform.py: combine()` — 종목별 결측 팩터 재정규화 포함 | 그대로 사용 |
| 실험 기록 | `research/experiment.py` — git commit 해시까지 기록 | 그대로 사용 |

가장 중요한 발견은 **이벤트 데이터셋의 뼈대가 이미 있다**는 것이다.
`data/fundamentals_panel.py`는 DART 재무를 패널에 넣으면서
`announcement_date`(DART 접수일)를 별도 컬럼으로 저장하고, `available_at`을
접수일의 **다음 거래일**로 잡는다. 이벤트 스터디에 필요한 "이벤트 시각"과
"사용 가능 시각"의 분리가 이미 되어 있다. 설계안 §29 Phase 1이 요구하는 것의
절반은 이미 존재한다.

> **정정 (§8.3 참조):** 구조는 맞지만 **날짜가 틀렸다.** `rcept_dt`는 재무제표를
> 담은 정기보고서의 접수일이고, 시장이 실적을 알게 된 날은 그보다 몇 주 앞선
> 잠정실적 공시일이다. 뼈대는 재사용할 수 있으나 이벤트 정의는 고쳐야 한다.

## 2. 막혀 있는 것 — 데이터

### 2.1 컨센서스는 없고, 공짜로 구할 수 없다

설계안의 다음 피처는 **현재 구할 방법이 없다**: `eps_consensus`,
`revenue_consensus`, `analyst_revision_7d/30d`, `target_price_revision`,
`estimate_dispersion`, `guidance_consensus`.

- DART는 실제치만 준다. 추정치 API가 없다.
- 한국 컨센서스는 FnGuide / WiseFn / Quantiwise 등 유료 벤더 영역이다.
- 더 큰 문제는 가격이 아니라 **PIT**다. 필요한 것은 "오늘 시점의 컨센서스"가
  아니라 "2019-04-25 시점에 시장이 갖고 있던 컨센서스"다. 벤더 스냅샷으로
  과거를 백테스트하면 그것이 정확히 설계안 §24.1이 금지한 행위다.

**대안 (권장): 컨센서스 없는 SUE.** PEAD 문헌의 원조 정의(Foster–Olsen–Shevlin
계열)는 애널리스트 컨센서스가 아니라 **계절 랜덤워크 시계열 모형**을 기대치로
쓴다.

```text
ΔX_q  = X_q − X_{q−4}                       # 전년 동기 대비 변화
δ     = 최근 8분기 ΔX 평균                    # drift
SUE   = (ΔX_q − δ) / σ(ΔX, 최근 8분기)
```

이것은 DART 데이터만으로 계산된다. "시장의 기대"는 아니지만 "단순 외삽 대비
서프라이즈"로는 성립하며, 애초에 PEAD가 발견된 방식이 이쪽이다. 컨센서스를
살 수 있게 될 때까지의 대체재가 아니라, 독립적으로 정당한 정의다.

**단, 선결 확인 사항이 있다.** DART `fnlttSinglAcntAll`의 손익계산서는 보고서
종류에 따라 `thstrm_amount`가 3개월치일 수도, 누적일 수도 있다(별도로
`thstrm_add_amount`가 누적을 담는다). 현재 `fundamentals_panel.py`는 이
구분을 하지 않고 `thstrm_amount`만 읽는다. 분기 자체를 비교하는 시계열 SUE를
만들려면 **여기부터 검증해야 한다.** 분기와 누적이 섞이면 SUE는 계산은 되고
값은 전부 틀린다 — 조용히 틀리는 종류의 오류라 가장 위험하다.

### 2.2 표본 수가 근본적으로 부족하다

| 유니버스 | 종목 | 데이터 시작 | 실적 이벤트 수 |
|---|---|---|---|
| `ai_semiconductor` (KR) | 5 | 2023-01 | ≈ 70 |
| `secondary_battery` (KR) | 5 | 2023-01 | ≈ 70 |
| `us_asset_rotation` (US) | 11 | 2007-01 | **0** (전부 ETF) |

설계안 §22가 첫 연구 문제로 "실적발표 후 1~20거래일 초과수익 예측"을 고른
것은 옳다. 이벤트 시점이 명확하고 표본이 충분하다는 이유인데, **이
저장소에서는 그 두 번째 이유가 성립하지 않는다.**

의미 있는 수준은 최소 수천 건이다. KOSPI200 + KOSDAQ150 ≈ 350종목 × 4분기 ×
10년 ≈ 14,000건. 그래야 §15가 요구하는 "상태별 비대칭"을 상태 구간마다
수백 건씩 놓고 볼 수 있다.

**따라서 Phase 0은 모듈 신설이 아니라 유니버스·기간 확보다.** 이것을 건너뛰고
`state/`, `events/`, `ml/` 디렉터리를 먼저 만들면, 측정할 수 없는 코드가
쌓인다.

유니버스를 350종목으로 넓힐 때 따라오는 문제도 미리 적어둔다.

- **생존자 편향.** `config/themes.toml`은 이미 `from` 없는 멤버를 거부하는
  규율을 갖고 있다. 350종목 규모에서는 지수 편입·편출 이력이 필요하고, 상장폐지
  종목의 가격 데이터도 남겨야 한다. 현재 구성종목으로 과거를 채우면 그 규율이
  형해화된다.
- **수집량.** 350종목 × 10년 일봉 + 수급 + 공매도 패널은 지금의 5종목 대비
  70배다. `data/pipeline.py`의 배치 시간과 캐시 크기를 먼저 가늠할 것.

### 2.3 뉴스 타임스탬프 아카이브가 없다

설계안 §11(가격이 먼저 움직이고 기사가 뒤따르는 문제)은 **이 문서에서 가장
날카로운 지적**이며, 지적 자체에 동의한다. 다만 구현하려면 과거 기사 아카이브와
신뢰할 수 있는 최초 게시 시각이 필요하고, 둘 다 없다.

- 네이버 뉴스 API는 검색 API이지 PIT 아카이브가 아니다. 소급 수집 시 게시
  시각의 신뢰도와 커버리지가 모두 문제가 된다.
- `news_novelty`(§10)는 임베딩 모델 의존성을 새로 들여온다. 현재 이 프로젝트에는
  ML 스택 자체가 없다(§3.6).

비용 대비 난이도가 가장 높고, 누수 위험도 가장 크다. 마지막에 둔다.

### 2.4 공매도는 실제로 지금 가능하다 — 유일하게 바로 되는 신규 데이터

`pykrx`는 이미 `pyproject.toml`의 의존성이고, 이 컨테이너에서 확인한 결과 다음
함수를 제공한다.

```text
get_shorting_balance_by_date        # 공매도 잔고 → short_interest, days_to_cover
get_shorting_volume_by_date         # 일별 공매도 거래량 → short_volume_ratio
get_shorting_investor_volume_by_date
```

`data/flows.py`가 `pykrx` 수급 데이터를 PanelStore에 넣는 패턴을 그대로 복제하면
된다. 예상 작업량은 `flows.py` 한 파일 수준이고, 설계안 §6.5(Short Crowding)와
가설 H3의 절반이 여기서 측정 가능해진다.

**단, 한국에는 공매도 금지 구간이 길다.** 2020년 3월~2021년 5월(전면 후 부분
재개), 2023년 11월~2025년 3월(전면 금지). 이 구간의 공매도 피처는 **결측이 아니라
제도적으로 0**이다. 구분 없이 학습시키면 모델은 "공매도 잔고 없음 = 상승"을
배우는데, 그 구간이 마침 상승장이었기 때문일 뿐이다. 금지 구간 더미 변수 또는
구간 제외가 필수다. 설계안 §27.4가 "공매도를 방향 신호로 쓰지 말라"고 경고한 것과
별개의, 한국 시장 고유의 함정이다.

## 3. 설계 자체에 대한 지적

여기부터는 데이터가 아니라 설계안의 내용 자체에 대한 이견이다.

### 3.1 제안된 모듈 트리를 그대로 만들면 기존 검증 하네스를 못 쓴다

**가장 중요한 통합 지적이다.**

설계안 §20은 `state/`, `events/`, `reaction/`, `ml/`을 새 최상위 디렉터리로
제안한다. 그런데 `state/`와 `reaction/`이 만들어내는 것은 전부 **"(날짜, 종목) →
스칼라"**, 즉 이 저장소의 `Factor` ABC(`factors/base.py`)와 정확히 같은 모양이다.

`factors/`에 넣고 `factors/registry.py`에 등록하면, 그 즉시
`research report --factors ...`가 IC / IC IR / 분위수 단조성 / 게이트 판정 /
walk-forward를 **공짜로** 붙여준다. 별도 트리로 만들면 그 하네스가 안 붙고,
같은 검증 코드를 두 번 쓰게 된다.

권장 매핑:

| 설계안 §20 | 이 저장소에서의 위치 | 이유 |
|---|---|---|
| `state/trend.py`, `crowding.py`, `positioning.py` | `factors/state.py` (`Factor` 서브클래스) | 기존 게이트·IC 하네스 상속 |
| `reaction/*.py` | `factors/reaction.py` | 위와 동일 |
| `state/classifier.py` | `research/regime.py` 확장 | 국면 판정이 이미 여기 있다 |
| `events/*.py` | `data/events.py` 수집기 + PanelStore 데이터셋 `events` | `flows.py` 패턴, PIT 메타 자동 |
| `ml/*.py` | `research/ml/` | 연구 도구지 실행 경로가 아니다 |
| `strategies/event_alpha.py` | 그대로 | 유일하게 위치가 맞는 항목 |

### 3.2 `ReactionEfficiency = Actual / Expected`는 쓰면 안 된다

설계안 §13. Expected가 0 근처면 발산하고, 부호가 다르면 값의 의미가 사라진다
(Expected −2%, Actual +2% → RE = −1.0인데 이것은 "역방향 반응"이지 "효율 −100%"가
아니다).

Residual(뺄셈, §12.3)만 쓰는 것이 맞다. 굳이 비율이 필요하면 분모 하한 클리핑과
부호 분리를 함께 넣어야 한다. 설계안에서 명확히 잘못된 유일한 수식이다.

### 3.3 Reaction Residual은 2단 모델이며, 여기에 누수가 숨는다

`ReactionResidual = ActualReaction − ExpectedReaction`에서 `ExpectedReaction`은
그 자체가 적합된 모델이다(§12.2). 이 모델을 전체 기간으로 한 번 적합한 뒤 잔차를
2단 모델의 피처로 넣으면, **미래 이벤트의 정보가 과거 시점의 잔차에 스며든다.**

필요한 것은 중첩(nested) walk-forward다. 각 테스트 창의 `ExpectedReaction` 모델은
그 창 시작 이전 데이터로만 적합해야 한다. 설계안은 이 점을 언급하지 않는데,
2단 구조에서 가장 흔한 사고 지점이다.

### 3.4 Purge만으로는 부족하다 — Embargo 길이를 명시해야 한다

§24.3은 "랜덤 split 금지"까지만 말한다. 라벨이 `future_20d_alpha`라면 **학습
구간의 마지막 날과 테스트 구간의 첫날 사이에 최소 20거래일의 embargo**가 필요하다.
없으면 학습 라벨이 테스트 구간의 가격을 들여다본다.

덧붙여, 같은 날짜에 발생한 여러 종목의 이벤트는 시장 요인으로 상관돼 있어
**유효 표본 수가 명목 표본 수보다 훨씬 적다.** 라벨을 초과수익(alpha)으로 잡은
설계안의 선택은 이 문제를 줄이는 방향으로 옳지만, 유의성을 판단할 때는 이벤트
클러스터링을 감안해야 한다. §2.2의 "수천 건이 필요하다"는 기준은 이 때문에 더
보수적으로 잡아야 한다.

### 3.5 기존 엔진은 캘린더 리밸런싱 전용이다 — 이벤트 전략은 새 포지션 수명주기가 필요하다

**설계안이 유일하게 전혀 다루지 않은 실행 문제다.**

현재 구조는 `on_bar` → `is_rebalance_date`(월말) → 목표 비중 벡터 전체 →
`plan_rebalance`다. 즉 **캘린더가 이끄는 횡단면 전량 재배분**이다.

이벤트 전략은 다르다. 이벤트일마다 개별 진입하고, N거래일 뒤에 개별 청산하며,
동시 보유 종목 수가 시점마다 변한다. `allocation/rebalance.py`의 목표 비중
모델과 맞지 않는다.

필요한 것:

- 이벤트 진입 큐 (이벤트일 종가 신호 → 다음 시가 체결, 기존 흐름 유지)
- 보유일 카운터 기반 만기 청산 — `rsi_reversion`이 이미 쓰는 패턴이고
  `strategies/state.py`로 영속화까지 된다
- 동시 보유 상한과 이벤트 집중 제한 (같은 주에 30건이 몰리는 경우)

또한 **회전율이 구조적으로 높아진다.** 20일 보유 × 분기 이벤트면 연 회전율이
쉽게 4~8에 이른다. `[promotion] max_annual_turnover = 6.0`에 ML보다 먼저
부딪힐 가능성이 크다. 설계안 §29는 Phase 5(ML) 다음에야 전략 통합을 두는데,
**회전율과 비용은 Phase 4에서 추정해야 한다.** 비용이 알파를 다 먹는다면
모델을 만들 이유가 없다.

### 3.6 적합 모델을 도입하는 순간 승격 하네스 자체를 고쳐야 한다

`research/evaluation.py`의 walk-forward는 결과에 `train_segments_used: False`를
명시하고, 리포트에도 "이 전략은 파라미터를 데이터로 맞추지 않는 규칙 기반이라
학습할 것이 없다"고 적는다. **모델을 적합하는 순간 이 전제가 깨진다.**

필요한 변경:

- 창별 재적합 경로 (지금은 테스트 구간만 실행한다)
- 모델 아티팩트 버전 기록 — `experiment.py`에 git commit 기록이 이미 있으니
  거기에 모델 해시와 시드를 붙이면 된다
- 난수 시드 고정 (LightGBM은 기본적으로 비결정적이다)

**추가 승격 기준을 하나 권장한다: IS→OOS 감쇠비** (예: `OOS IC ≥ IS IC × 0.5`).
현재 6개 기준은 규칙 기반 전략을 전제로 설계돼 있어서, 학습 구간을 암기한
모델을 걸러내지 못한다. 적합 모델을 들이면서 이 기준을 안 넣으면 게이트가
느슨해진다.

### 3.7 LLM 추출은 실행 경로가 아니라 데이터 소스로 취급해야 한다

설계안 §9의 방향(직접 매매판단 금지, 고정 스키마 추출)에 동의한다. 다만
재현성을 지키려면 다음이 강제되어야 한다.

- **백테스트 실행 중 LLM 호출 금지.** 사전 추출해서 PanelStore에 저장한 뒤
  읽기만 한다.
- `attach_metadata(source="llm:<model_id>", data_version="<prompt_version>",
  available_at=<기사 시각의 다음 거래일>)` — 기존 패널 스키마가 정확히 이
  용도에 맞는다. 새 구조가 필요 없다.
- `data_version`이 바뀌면(프롬프트 수정, 모델 교체) 이전 추출 결과와 섞지 않는다.
  모델이 폐기되면 동일 재추출이 불가능해지므로, 버전 경계를 넘는 학습 데이터는
  재현 불가능한 데이터다.

## 4. 권장 적용 순서 (수정안)

각 Phase는 **다음으로 넘어갈 조건**을 함께 정의한다. 조건을 못 채우면 다음
Phase로 가지 않는다 — 이것이 설계안 §29와 가장 크게 다른 점이다.

### Phase 0 — 표본 확보 (선행 필수, 신규 모듈 없음)

- KR 유니버스를 KOSPI200 + KOSDAQ150 규모로 확장, 편입·편출 이력 포함
- 가격·수급 패널을 2015년 이후로 소급 수집
- **넘어갈 조건:** 이벤트 후보 수 ≥ 3,000건, 생존자 편향 대책 문서화

### Phase 1 — 가격 기반 State 팩터 (신규 데이터 0)

`factors/state.py`에 `Factor` 서브클래스로 추가. 전부 기존 OHLCV만 쓴다.

- `return_5d/20d/60d/120d`, `price_vs_ma20/60/200`
- `momentum_acceleration_5_20`, `momentum_acceleration_20_60`
- `anchored_vwap_60` 기반 `unrealized_gain_proxy` (§6.4 — 이름이 말하듯
  proxy임을 docstring에 명시)
- `volume_z`, `turnover_z`
- **넘어갈 조건:** `research report`로 IC 측정 완료. 게이트 통과 여부와 무관하게
  **측정이 되는 것** 자체가 조건이다.

### Phase 2 — 공매도 패널 (§2.4)

- `data/short_interest.py` + PanelStore 데이터셋, 금지 구간 더미 포함
- `factors/positioning.py`: `days_to_cover`, `short_balance_ratio`
- **넘어갈 조건:** 금지 구간을 제외한 유효 관측이 종목당 충분한지 확인

### Phase 3 — 이벤트 데이터셋 (컨센서스 없이)

- `data/events.py`: DART 접수일 기준 이벤트 테이블
- 시계열 SUE (§2.1). 그 전에 분기/누적 구분 검증
- **넘어갈 조건:** 이벤트당 pre-event state 피처와 post-event 수익률이 모두
  채워진 행이 3,000건 이상

### Phase 4 — 이벤트 스터디 (기술통계, ML 없음) ← **판단 분기점**

`research event-study` 명령 신설. 주는 것은 예측이 아니라 표다.

```text
CAR(−60, −1)  분위 × SUE 분위  →  CAR(+1, +20) 평균 / 중앙값 / 승률 / 표본수
```

**이 표 하나로 설계안의 H1·H2·H5를 ML 없이 1차 검증할 수 있다.**

- H1(surprise × crowding): pre-runup 상위 분위에서 SUE 효과가 실제로 줄어드는가
- H2(reaction residual): 이벤트 당일 반응이 약했던 그룹의 이후 20일이 다른가
- H5(상태별 비대칭): 상태 구간별로 같은 SUE의 효과가 다른가

**넘어갈 조건:** 3,000~5,000건 표본의 2차원 분위 표에서 효과가 **눈에 보일 것.**
여기서 안 보이면 LightGBM은 잡음을 찾을 뿐이다. 보이지 않으면 Phase 5로 가지
않는다 — 이 판정이 이 계획에서 가장 중요한 지점이다.

또한 이 단계에서 **회전율과 비용을 추정한다**(§3.5). 이벤트 전략의 예상 연
회전율을 계산해 `max_annual_turnover = 6.0`과 대조한다.

### Phase 5 — ML (Phase 4가 신호를 보여준 경우에만)

- LightGBM baseline, purged walk-forward + 20거래일 embargo(§3.4)
- ExpectedReaction 2단 모델은 중첩 적합(§3.3)
- 피처 예산 상한을 미리 정한다. 표본 3,000건에 피처 40개는 여전히 많다
- 승격 하네스 개조(§3.6)와 IS→OOS 감쇠비 기준 추가
- 신규 의존성: `lightgbm`, `shap`, `scikit-learn`

### Phase 6 — 전략 통합

- `strategies/event_alpha.py` + 이벤트 포지션 수명주기(§3.5)
- 기존 structural 팩터와 결합, 가중치는 OOS로 결정
- `research evaluate` 승격 판정

### 별도 트랙 (최후) — 뉴스 / LLM

Phase 4가 명확한 신호를 보여주고 Phase 6까지 간 뒤에 착수한다. §2.3의 데이터
문제와 §3.7의 재현성 제약을 먼저 해결해야 한다.

## 7. 요약

설계안은 **"무엇을 만들 것인가"에 대해서는 대체로 옳다.** 절대값보다
기대 대비 변화, 뉴스보다 가격 반응, 선형 결합보다 상태 × 이벤트 상호작용 —
세 원칙 모두 이 저장소가 지금 부딪힌 벽(팩터 IC IR이 게이트를 못 넘는 상황)에
대한 합당한 대응이다.

**"무엇부터 만들 수 있는가"에 대해서는 이 저장소의 현실을 모른 채 쓰였다.**
컨센서스가 없고, 이벤트 표본이 70건이며, 미국 유니버스는 실적발표가 없는
ETF다. 제안된 Phase 1~7을 순서대로 따르면 Phase 1에서 데이터가 없어 멈춘다.

순서를 데이터 가용성 기준으로 재배열하고(§4), 모듈을 기존 `Factor` 하네스
안으로 접고(§3.1), ML 전에 이벤트 스터디로 신호 유무를 먼저 판정하면(Phase 4),
설계안의 핵심은 그대로 살릴 수 있다.

**하지 말 것:** 표본 70건에 LightGBM을 돌리는 것. 그리고 Phase 0을 건너뛰고
`state/`·`events/`·`ml/` 디렉터리부터 만드는 것 — 측정할 수 없는 코드는
이 프로젝트가 지금까지 지켜온 "OOS 증거 > 직관" 원칙의 반대편에 있다.

# 8. 2차 검토 (`trading_bot_event_alpha_superpowers_review.md`)

같은 날 도착한 재검토 문서에 대한 검토다. 1차 제안을 스스로 수정한 문서이며,
방법론 면에서 상당히 개선됐다.

## 8.1 판정: 방법론은 해결됐고, 데이터 문제는 시장을 옮겼을 뿐 그대로다

1차 검토에서 지적한 항목의 처리 현황:

| 1차 검토 지적 | 2차 문서의 처리 | 상태 |
|---|---|---|
| §3.2 `ReactionEfficiency` 비율이 발산한다 | §7에서 Residual만 남기고 비율을 삭제 | **해결** |
| ML을 너무 일찍 쓴다 | §17 null model, §18 복잡도 사다리, Phase 4 → 5 | **해결** |
| LLM 조기 도입 | §10에서 보류, Phase 8로 이동 | **해결** |
| 이벤트 스터디를 ML 앞에 둘 것 | §5, Phase 3 — 1차 검토 Phase 4와 같은 결론 | **해결** |
| §2.2 표본 70건 | §20에서 미국 개별주 500~1000으로 이동 | **방향은 해결, 새 문제 발생 (§8.5, §8.6)** |
| §3.3 2단 모델 누수 | §8이 Model A/B를 분리했으나 중첩 재적합은 여전히 미언급 | **미해결** |
| §3.4 embargo 길이 | §26이 walk-forward를 나열하나 수치 없음 | **미해결** |
| §2.1 컨센서스 부재 | §21이 "Consensus 확보 가능"으로 단정 | **미해결 (§8.2)** |
| §3.1 모듈 트리 | 2차 문서는 코드 구조를 다루지 않음 | 1차 검토 매핑 권고 유효 |
| §3.5 이벤트 포지션 수명주기 | §15 Overlay가 우회 | **부분 해결, 새 제약 (§8.4)** |
| §3.6 승격 하네스 개조 | 미언급 | **미해결** |

2차 문서가 새로 도입한 것 중 1차 검토가 다루지 않았고 **명백히 옳은** 것이 있다.
**§4 — 상태 라벨(`CROWDED_UPTREND` 등)을 초기에 만들지 않고 연속형 피처로
유지한다.** `-30%면 depressed인가 -40%인가`를 손으로 정하는 것은 in-sample
파라미터 스윕과 같은 종류의 행위이고, 이 저장소는 그 함정의 실물 사례를 이미
갖고 있다(`us_etf_rotation_review.md`: "in-sample 스윕 승자를 그대로 채택하면
안 되는 이유의 실물 사례"). 1차 검토는 이 위험을 짚지 않았다.

## 8.2 §21 "미국은 컨센서스 확보 가능"은 절반만 맞다

**확인하지 못한 것을 먼저 밝힌다.** Yahoo 도메인이 이 실행 환경의 네트워크
정책에 차단돼 있어 `yfinance` 실측을 하지 못했다. 아래는 코드 확인이 아니라
알려진 API 사양에 근거하며, 착수 전에 실측으로 재확인해야 한다.

무료로 얻을 수 있는 것은 **이벤트당 컨센서스 숫자 한 개의 최근 몇 년치**다.
`yfinance`의 실적 발표 이력은 대체로 최근 3년 안팎이고, 거기 붙은 EPS 추정치는
"그 시점에 시장이 갖고 있던 컨센서스"가 아니라 **오늘 조회한 값**이다. 설계안이
요구하는 추정치의 **변화 경로**(`analyst_revision_7d/30d`,
`estimate_dispersion`, `target_price_revision`)는 아예 없다.

즉 1차 검토 §2.1이 한국에 대해 지적한 문제 — 오늘의 스냅샷으로 과거를
백테스트하면 그것이 §24.1 위반이다 — 가 미국에서 그대로 반복된다. **시장만
바뀌었고 문제는 남았다.** 500~1000종목 × 15년치 PIT 컨센서스는 유료 벤더
(Alpha Vantage / Finnhub / FMP / Sharadar / Zacks) 영역이고, 무료 티어의 호출
한도로는 종목 수부터 불가능하다.

**무료로 진짜 얻을 수 있는 것은 실제치다: SEC EDGAR.** `companyfacts` API가 전
미국 신고기업의 XBRL 재무를 `filed`(접수일) 필드와 함께 제공한다. API 키가
필요 없다. 이것은 DART의 미국판이고, **1차 검토 §2.1이 제안한 시계열 SUE의
입력으로 정확히 맞는다.**

결론은 바뀌지 않는다. 시장을 미국으로 옮겨도 **컨센서스 기반 설계(§7.1의
`consensus_dispersion` 포함)는 만들 수 없고, 만들 수 있는 것은 시계열 SUE다.**

## 8.3 이벤트 날짜가 틀렸다 — 1차 검토도 함께 놓친 것

**두 문서와 1차 검토가 모두 놓쳤고, 다른 모든 것의 전제가 되는 문제다.**

1차 검토는 "`fundamentals_panel.py`가 `announcement_date`를 저장하니 이벤트
데이터셋 뼈대가 이미 있다"고 판단했다. 구조는 맞지만 **그 날짜는 시장이 실적을
알게 된 날이 아니다.**

- **한국:** 대형주는 **잠정실적을 공정공시로 먼저** 낸다. 삼성전자 4분기 잠정실적은
  1월 초에 나오고, 그 숫자를 담은 사업보고서 접수는 3월이다. **주가가 반응하는
  것은 1월이다.** 현재 코드가 이벤트일로 쓸 `rcept_dt`는 3월을 가리킨다.
- **미국:** 같은 구조다. 실적 발표는 8-K Item 2.02(Results of Operations)
  보도자료이고, 10-Q는 그보다 며칠에서 수 주 뒤다.

결과가 조용해서 위험하다. 이벤트일을 정기보고서 접수일로 잡으면 pre-event
state는 **이미 실적 반응이 끝난 뒤의 상태**를 재고, immediate reaction은 **아무
일도 없었던 날**을 잰다. 코드는 정상 동작하고, 숫자는 나오고, **이벤트 스터디
전체가 무효가 된다.**

고치는 방법은 어렵지 않다.

- KR: `DartClient.disclosure_list`가 이미 `report_name`을 반환한다. "연결재무제표기준
  영업(잠정)실적" 계열 보고서명을 이벤트로 잡는 필터를 추가하면 된다.
- US: EDGAR 8-K 중 Item 2.02를 이벤트로 잡는다.

2차 문서 §23 Phase 1이 수집 항목에 `announcement_time`을 넣은 것은 방향이 맞지만,
**"어느 공시가 이벤트인가"를 정의하지 않았다.** 이것이 Phase 1의 첫 번째 설계
결정이어야 한다.

## 8.4 Overlay(§14~16)는 좋은 판단이다 — 다만 리밸런싱 주기와 충돌한다

이 저장소 기준으로 오버레이 접근이 좋은 이유는 세 가지이고, 전부 코드로 확인된다.

1. **1차 검토 §3.5의 반대를 실제로 해소한다.** 이벤트 진입/만기청산 수명주기가
   기존 엔진과 안 맞는다는 문제를, 구조 전략이 계속 캘린더를 이끌게 두고
   오버레이는 비중만 조정하는 방식으로 우회한다.
2. **기존 합성 체인에 그대로 붙는다.** `theme_multifactor.generate_targets`는
   이미 `base weights → scale_weights(regime) → apply_constraints` 순서로
   합성한다. 여기에 `apply_event_overlay` 한 단계를 더하는 것은 `allocation/`에
   모듈 하나와 전략 쪽 10줄 수준이다.
3. **측정이 실제로 공짜다.** `research evaluate --config with_overlay.toml
   --benchmark-config without_overlay.toml`은 **같은 전략을 두 설정으로 돌려**
   차이를 낸다(`cli.py:436`, `evaluation.py:360`). 오버레이 효과만 분리해 기존
   승격 하네스로 재는 데 신규 코드가 0이다. §16이 "효과를 독립적으로 측정
   가능"이라 쓴 것이 이 저장소에서 문자 그대로 성립한다.

**그러나 제약이 있다.** 현재 `on_bar`는 `is_rebalance_date`(월말)가 아니면 즉시
return한다. 월 초에 발생한 이벤트를 월말에야 반영하면 20거래일 알파 구간이 이미
끝나 있다. 오버레이에는 **리밸런싱 주기와 무관한 일별 경로**가 필요하고, 그 경로는
지금 전략 구조에 없다. 신규 코드가 0이라는 것은 *측정*에 대해서만 참이고
*구현*에는 해당하지 않는다.

## 8.5 §15 Overlay와 §20 미국 개별주는 이 저장소에서 양립하지 않는다

2차 문서 내부의 모순이다.

- §15의 오버레이는 **깔고 앉을 구조 전략**을 전제한다.
- §20은 연구 대상을 미국 개별주로 옮긴다.
- 그런데 이 저장소의 구조 전략은 KR 테마 5종목과 US ETF 11종뿐이다. **미국
  개별주 이벤트 모델은 오버레이할 대상이 없다.**

선택지는 셋이고 문서는 고르지 않았다.

- **(a) 연구·배치를 모두 미국 개별주로 옮긴다.** 미국 개별주 구조 전략을 새로
  만들어야 한다. 부수 효과로 ETF 11종의 "분위당 2.2종목" 문제도 함께 풀린다.
  사실상 프로젝트 재정렬이다.
- **(b) 연구는 미국(표본), 배치는 한국(오버레이).** 효과가 KR 부분표본에서도
  재현되는지 별도 확인이 필수다. 재현되지 않으면 배치할 수 없다.
- **(c) 한국에 머문다.** KOSPI200+KOSDAQ150로 넓히면 완화되지만 미국만큼의
  표본은 안 된다.

**추천은 (a)이되 규모를 낮춘 형태다** — S&P 500 구성종목이 아니라 **유동성 상위
300~500종목, 2010년 이후.** 이유는 §8.6이다.

## 8.6 §20이 새로 들여온 문제: 생존자 편향과 상장폐지 종목 가격

S&P 500의 현재 구성종목으로 과거를 채우면 생존자 편향이다. `themes.toml`이 `from`
없는 멤버를 거부하며 지켜온 규율이 500종목 규모에서 가장 무너지기 쉽다.

- 과거 구성종목 이력을 무료로 신뢰도 있게 얻기 어렵다.
- **PIT-안전한 대안: 구성종목 목록을 쓰지 말고 자기 데이터로 유니버스를
  재구성한다.** 각 리밸런싱 시점에서 "그 시점까지의 20일 평균 거래대금 상위 N"으로
  정의하면 미래 정보가 들어갈 수 없다. `research.toml`에 `min_avg_value_20d`
  개념이 이미 있다.
- **그래도 남는 진짜 난제는 상장폐지 종목의 가격 데이터다.** FinanceDataReader와
  Yahoo는 상폐 티커를 제대로 주지 않는다. 이 데이터가 없으면 유니버스를 어떻게
  정의하든 편향이 남는다. 미국 개별주 연구에서 가장 어려운 무료 데이터 문제다.
- 정직한 완화책: (1) 대형주로 제한 — 상폐가 드물고 대부분 M&A다, (2) EDGAR 신고
  기업 수 대비 가격 확보 기업 수를 세어 **편향의 크기를 측정해 리포트에 적는다**,
  (3) 해결됐다고 주장하지 않는다.

## 8.7 2차 문서에도 여전히 비어 있는 것

1. **Embargo 길이.** §26이 walk-forward를 나열하지만, 20일 라벨에 필요한 최소
   20거래일 embargo가 없다(1차 §3.4).
2. **2단 모델의 중첩 재적합.** §8이 Model A/B를 분리한 것은 옳지만, Model A를 전
   기간으로 한 번 적합하면 잔차에 미래가 들어간다(1차 §3.3).
3. **표본 수의 정량 기준.** §27은 "sufficient sample size"라고만 한다. 상호작용
   검정은 **칸 단위로** 표본이 필요하다 — SUE 5분위 × pre-runup 5분위 = 25칸,
   칸당 수백 건이면 하한이 6,000건 이상이다.
4. **비용의 정량화.** §27은 "cost-adjusted"라고만 한다. 오버레이는 독립 이벤트
   전략보다 회전율이 낮아 유리하지만, 얼마나 유리한지는 재봐야 한다.
5. **승격 하네스 개조.** §18의 복잡도 사다리는 "ML이 baseline을 OOS에서 이겼는가"라는
   판정을 요구하는데, **그 판정을 낼 도구가 지금 없다.** `evaluation.py`는
   `train_segments_used: False`를 전제로 만들어져 있다(1차 §3.6).

## 8.8 두 문서 모두 놓친, 지금 가장 싼 첫 삽

**이벤트 리스크 오버레이는 컨센서스도 서프라이즈도 필요 없다. 실적 발표 "날짜"만
있으면 된다.**

가설: *실적 발표를 앞둔 종목의 비중을 발표 전 N일 동안 축소하면 위험조정 성과가
개선되는가?*

- 필요 데이터: 과거 실적 발표일 — DART 공시목록으로 수집 가능(§8.3의 잠정실적
  필터만 추가하면 된다)
- 필요 예측: 없음. 다음 발표일은 전년 동기 + 계절 오프셋으로 PIT-안전하게 근사한다
- 필요 모델: 없음
- 측정: `research evaluate --benchmark-config`로 오버레이 유무 비교(§8.4)
- 대상: 지금 있는 KR 5종목 테마 전략

표본이 작아 성과 결론은 약하다. 그러나 이 작업이 확인하는 것은 성과가 아니라
**배관이다** — 이벤트 날짜 수집 → 오버레이 적용 → 승격 하네스 판정까지 끝에서
끝까지 붙는지. 2차 문서 §32의 사슬을 가장 짧은 경로로 한 번 완주하는 방법이고,
**여기서 안 붙으면 미국 500종목을 수집해도 안 붙는다.**

## 8.9 수정된 순서 (1차·2차 통합)

| Phase | 내용 | 근거 |
|---|---|---|
| 0 | **배관 완주** — 이벤트 리스크 오버레이, KR 5종목, 신규 데이터 ≈ 0 | §8.8 |
| 1 | **이벤트 날짜 정의 정정** — KR 잠정실적 / US 8-K 2.02 | §8.3 |
| 2 | **유니버스** — 미국 유동성 상위 300~500, 2010~, PIT 재구성 + 편향 측정 | §8.5(a), §8.6 |
| 3 | **EDGAR `companyfacts` 수집 + 시계열 SUE** | §8.2, 1차 §2.1 |
| 4 | **최소 state 피처** — 2차 문서 §23 Phase 2 목록을 `Factor`로 | 1차 §3.1 |
| 5 | **이벤트 스터디 / 가설 검정 (H1·H2)** ← go/no-go | 1차 Phase 4, 2차 §5 |
| 6 | **선형 baseline + interaction** (null model) | 2차 §17 |
| 7 | **ML** — baseline을 OOS에서 이길 때만. 승격 하네스 개조 동반 | 2차 §18, 1차 §3.6 |
| 8 | **오버레이 배치** | 2차 §15 |

1차 검토의 순서와 달라진 점: 앞에 Phase 0(배관 완주)과 Phase 1(이벤트 날짜
정정)이 붙었고, 대상 시장이 KR에서 US로 바뀌었으며, ML 앞에 선형 baseline 관문이
추가됐다. Phase 1은 순서상 뒤로 미룰 수 없다 — 이벤트 날짜가 틀린 채로 만든
데이터셋은 이후 전부를 무효로 만든다.

## 8.10 2차 검토 총평

1차 제안이 "무엇을 만들까"에 대한 문서였다면, 2차 문서는 **"어떻게 검증할까"에
제대로 답했다.** §17(null model), §18(복잡도 사다리), §4(상태 라벨 유보),
§15(오버레이)는 전부 이 저장소가 이미 비싸게 배운 교훈과 같은 방향이고, 그중
오버레이는 1차 검토가 제기한 구조적 반대를 실제로 해소한다.

남은 문제는 데이터 하나로 좁혀졌고, **그 문제는 시장을 옮겨도 사라지지 않는다.**
컨센서스는 미국에서도 무료 PIT로 얻을 수 없고(§8.2), 이벤트 날짜는 두 시장 모두
지금 코드가 잘못 잡고 있다(§8.3). 전자는 시계열 SUE로 우회할 수 있고, 후자는
우회로가 없으니 고쳐야 한다.
